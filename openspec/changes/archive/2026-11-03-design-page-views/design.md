# Design

## Context

Today (`viewer/`): `app.js` routes `selection` and `browse`; `views/panel.js` is a left list of every option with toggle/view actions, shown on Selection only; `views/modal.js` shows node detail over any page; `views/browse.js` is a tree; `views/selection.js` renders the brief, conflicts, missing, chosen options and undecided. The selection and the open node live in the hash (`pick`, `view`). `select.js` has `toggle`, `analyze`, `undecided`. The app is static, no build step for the viewer, plain ES modules and a small `el()` helper. The `edit-mode` change (unapplied) adds controls to the Selection page.

## Goals / Non-Goals

**Goals:**
- Give Graph, Design and Node separate roles and remove the side panel and the modal.
- Show the selection as a generated block diagram at the top of Design.
- Keep all state in the URL and all old links working.

**Non-Goals:**
- New data, images, per-node drawings, a physical schematic, AI generation changes, a solver, edit-mode changes.

## Decisions

**Pages `design` and `graph`; node is a parameter, not a page.** `view=<id>` already exists and survives navigation. `design` is the default; `selection` and `browse` are parsed as aliases and rewritten on the next link build. Alternative: a `#/node/<id>` route. Rejected: the node must appear next to the current page (drawer) or in it (Graph), so it cannot replace the page.

**Tray instead of panel; choosing happens in node views.** The tray only summarises (chips, counts, Reset). Choosing options moves to the decision node view (all options of one decision, with exclusion reasons) and to the option node view. This keeps the exclusion feedback of the panel where the decision is made, and removes the long always-on list. Alternative: make the panel collapsible. Rejected: still mixes navigation and state. The diagram boxes are the entry point for "I want to decide this": they open the decision in the drawer.

**One node-view renderer, two mounts.** `views/node.js` renders the detail (moved from the modal, plus the option list for decisions); `app.js` mounts it in a drawer element on Design and in the main pane on Graph. Drawer is a plain aside in a two-column grid (stacked and full width on narrow screens), not an overlay, so the diagram stays clickable. Esc and the close link remove `view`.

**Slot lives on decisions, options inherit.** `slot` is validated on any node but the diagram only reads it from decisions. A decision is one box; slots become Mermaid subgraphs. This is the smallest model that gives "empty slots shown as undecided" without a new node type.

**Diagram generated by a pure function.** `viewer/diagram.js` exports `buildDiagram(graph, pick) -> string` (a Mermaid `flowchart LR`), using `analyze` for conflicts and missing requirements. Edges are drawn between decisions, derived from direct `requires` of chosen options only (same rule as the rest of the viewer). Titles are escaped by quoting labels and replacing `"`, `<`, `>`, `[`, `]` with entities. Box clicks use Mermaid `click` directives with `securityLevel: 'strict'` disabled for clicks only if needed; otherwise the view attaches listeners to the rendered nodes by id. Pure output makes it testable with `node --test` without a browser.

**Mermaid loaded lazily from a pinned jsdelivr URL.** Dynamic `import()` of the ESM build at first Design render; on failure show the source in a `<pre>`. Alternative: vendor the file (about 3 MB) into `viewer/vendor/`. Chosen against for a demo; easy to switch since loading is isolated in one function.

**Old URL support in `hash.js`.** `parseHash` returns `page: 'design' | 'graph'`; `buildHash` always writes the new names.

## Risks / Trade-offs

- Choosing options is now less direct than with the always-visible list. Mitigation: diagram boxes and the decision node view; revisit with the user after trying it.
- Mermaid layout may be cluttered with many slots or edges. Mitigation: edges only between decisions, only chosen requirements; revisit when the graph grows.
- A CDN dependency makes the first load need the network. Mitigation: the text fallback; vendoring is a small follow-up.
- `edit-mode` tasks refer to the Selection page and panel; they need renaming when applied after this change.
